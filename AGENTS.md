# AGENTS.md

Conventions for anyone (human or coding agent) working in this repo.

## What this is

The personal site at [nikolapacekvetnic.rs](https://nikolapacekvetnic.rs): a desktop-style interface (icons, windows, taskbar) with a blog, portfolio and music. It replaces an older WordPress site.

## Stack

- React 19, TypeScript, React Router 8 in framework mode, Vite 8.
- `ssr: false` with pre-rendering (`react-router.config.ts`): the build in `build/client` is static HTML, JS and CSS.
- Plain CSS, one stylesheet per component, BEM-style class names (`desktop-icon__caption`). Colours in window content, accents and the wallpaper come from the tokens on `:root` in `app/app.css`, as `rgb(var(--text))` or `rgb(var(--accent) / 0.1)`, so the appearance settings reach them; never write those as literals. Text in window content is sized in `rem`, so the text-size setting reaches it; the chrome (taskbar, title bars, icon captions, menus) sizes its text in `px`, as it does its bars.
- Hosting is shared Apache hosting (PHP and MySQL available, no Node runtime). Anything dynamic later goes into small PHP scripts under `api/`.
- Apache serves the build by the rules in `public/.htaccess`: a page at its path, with or without a trailing slash, unknown paths from `__spa-fallback.html` with a 404, never another page's HTML. `npm run preview` serves the same HTML at the same URLs (`vite.config.ts`), so change the two together. The hosting's LiteSpeed applies only part of the file and adds a trailing slash to folders whatever it says, so never redirect a slash away there (the two redirects loop), and the app doesn't rely on the file: `entry.client.tsx` drops a trailing slash from the address before the router starts.
- Every push to `main` that passes CI is deployed to staging.nikolapacekvetnic.rs over FTPS (the `deploy-staging` job, secrets in the `staging` environment). Staging is kept out of search engines.

## Commands

| Command                           | What it does                         |

## Rules for the code

- Every route is rendered at build time in Node. Do not touch `window`, `document` or `localStorage` during render; use effects or event handlers.
- No `action` or `headers` exports in routes: there is no server to run them.
- Route modules (`app/routes/*`) may use `loader` only for data that is known at build time.
- Every page is a child of the layout route in `app/routes.ts`, which draws the desktop. A page route exports `meta` (built with `getPageMeta` from `app/meta.ts`), may export a build-time `loader`, and renders nothing: its window shows the loaded data through `AppContent`. The URL is the focused window's path, and `Shell` keeps the two in step. Any other address matches the catch-all `routes/not-found.tsx`: the desktop with a notice. A route the host serves through the SPA fallback (unknown posts, unknown addresses) needs a `clientLoader`, so its first render is as empty as that HTML.
- Code that needs Node (the file system, Markdown) lives in `*.server.ts` files, so it never reaches the browser bundle.
- The taskbar's logo opens the start menu (`components/Taskbar/StartMenu.tsx`): every app as a tile, those in folders under their folder's title, and a search field (`app/desktop/search.ts`) that finds apps by title, folder and description. Its Restart button plays the boot screen again. The strip at the taskbar's far right shows the desktop; on a phone the logo does that instead.
- Small screens get the phone layout: a home screen and full-screen apps. Media queries draw it, so the pre-rendered page is right before any script runs; `usePhoneLayout` only switches behaviour (dragging, what a tap does). The query is written out in `usePhoneLayout.ts` and in each stylesheet that uses it, so change them together.
- On the desktop (not the phone), icons are selected by a click, a box drawn over the empty desktop, or Ctrl/Cmd and a click to add one; dragging a selected icon moves the whole selection (`moveManyToCells` in `app/desktop/drag.ts`).
- The visitor's appearance settings live in `app/settings/settings.ts` and in their browser's storage. `applyStoredSettings` puts them on `<html>` (`data-theme`, …), where the stylesheets read them; its source also runs as the inline script in `<head>` that applies them before the first paint, so it must stay self-contained: no imports or names from outside the function (a test runs it from its text). A new setting goes into `Settings`, `SETTING_VALUES` and `DEFAULT_SETTINGS`, and into that function if the stylesheets need it. Components read settings with `useSettings`.
- The first page of a visit, if it's the home page, opens with a short boot screen (`app/boot/boot.ts`, `components/Boot`): `startBoot` decides, before the first paint, as a second inline script in `<head>` (self-contained, like `applyStoredSettings`, and tested from its text), and sets `data-boot` on `<html>`; `Boot.css` times everything and ends it without any script. Any press or key skips it; it never plays for visitors who ask for less motion.
- The apps are listed in `app/desktop/apps.ts`, in their fresh-desktop order. An app can sit in a folder app instead of on the desktop (`folder`; the folder's window lists it as an icon, under a heading if it has a `group`, as Other in Games), live at a path of its own (`path`, e.g. `/games/sodhara`; the longest matching path wins), open its window at a size of its own (`windowSize`), be a page of its own shown edge to edge in an iframe (`page`), or lay out its window itself, scrolling its own content beside parts that stay put (`fills`, as the Blog does for its search bar), or show a page of its own from Markdown (`content: "games"`, see Content).
- A game's landing page is a small React app of its own in `games/<game>/` (plain JavaScript, its own look), built by `npm run build:games` into `public/apps/<game>/` (ignored by git) before `dev` and `build`, and served at `/apps/<game>/`, which its app's `page` points to. Edit it there; `npx vite --config games/<game>/vite.config.ts` gives it a dev server of its own, and a new one needs its line in `build:games`. A link in it to another page of the site asks the site to open it (`window.parent.postMessage({ type: "open", path })`, see `games/knossos/src/site.js` and `AppPage`), so it opens in the site's own window. Keep its media light: clips as WebM with an MP4 fallback, images as WebP.
- A window grows out of the control pressed just before it opened (an icon, a link, a widget's button), whatever opened it, and shrinks into its taskbar button when minimized (`app/desktop/launch.ts`, played by `AppWindow`); for visitors who ask for less motion it only fades.
- After the minutes the Settings give (`screensaver`, 5 by default) without a press, a move or a key, the screensaver dims the screen and floats the logo (`components/Screensaver`). It waits while a player or game page has focus (iframes, whose presses the page never sees), while something plays with sound, in a hidden tab and with reduced motion, and never runs in the phone layout.
- Keep components small and match the surrounding style.

## Content

- Blog posts are `content/blog/<slug>.md`: YAML front matter with `title`, `date` (`YYYY-MM-DD`), `summary` and optional `tags`, then Markdown. The file name is the URL (`/blog/<slug>`): lowercase letters and digits joined by hyphens.
- A post's images go in `public/blog/<slug>/` and are written by file name: `![Alt text](photo.jpg "Caption")`. An image on a line of its own becomes a figure, its title the caption. A WebM written the same way (`![Alt text](clip.webm "Caption")`) is a clip that plays silently on a loop, like an animated picture, and waits with its controls for visitors who ask for less motion; its MP4 goes beside it (`clip.mp4`), for browsers without WebM.
- A post with a missing or malformed field, or a local image that isn't there, fails the build, with the post's name in the message.
- Projects are `content/projects/<slug>.md`, shown as cards in the Projects window and each at `/projects/<slug>`: front matter `title`, `summary` (the card's line), `years` (`2021` or `2020–2021`, en dash), `status` (`finished` or `in-progress`), `tech` (a list), `repo` (an `https://` link) and optional `image` (the card's picture, a file name) and `featured` (`true` puts it before the others), then Markdown. A summary with `: ` in it needs quotes. Their images go in `public/projects/<slug>/`, written by file name as in posts; images on consecutive lines sit side by side as a row. A missing or malformed field, or a missing image, fails the build. Featured projects are listed first, then the most recent.
- The small games in the Games folder (Dungeon Gunner, Rogue C) are `content/games/<id>.md`, each the page of the app with that id (`content: "games"`, `group: "Other"`, `path: "/games/<id>"`), shown in its own window: front matter `title`, `summary`, `years` (as in projects), `tech` (a list) and optional `repo` (an `https://` link), then Markdown; images in `public/games/<id>/`. A game page without its app, or an app without its page, fails a test; a missing or malformed field fails the build. The bigger games (SODHARA, K'NOSSOS, VSEVOLOD) have landing pages instead (see Rules for the code).
- The desktop's widgets, behind the windows in its top right corner, show the newest post and the featured card, `content/featured.md`: front matter only, `title`, `text` (a sentence or two), `date` (the day it was written, `YYYY-MM-DD`, shown on the card), `link` (a page of the site, `/music/…`, which opens in its window, or an `https://` link) and optional `label` (the button, `Open` if left out) and `image` (a file in `public/`, from the site root). Without the file there's no card; a missing or malformed field, or a missing image, fails the build. Both come from the content at build time, as the module `virtual:desktop-widgets` (the plugin in `vite.config.ts`, `app/desktop/widgets.server.ts`), not from a loader: the desktop is drawn around every page, the SPA fallback's included. On the phone, only the newest post shows, above the icons.
- Open-source contributions are `content/open-source.yml`, on the Projects window's Open source tab (`/projects/open-source`): each upstream project once (`project`, `about`, `url`), with its `contributions` (`summary`, `date` merged as `YYYY-MM-DD`, `link` to the pull or merge request). Newest first, whatever the file's order; a missing or malformed field fails the build. A project can't be called `open-source`.
- Music is `content/music/<slug>.md`, a card on one of the Music window's tabs and each at `/music/<slug>`: front matter `title`, `kind` (`composition` for the Compositions tab at `/music`, `band` for Bands at `/music/bands`, `soundtrack` for Soundtracks at `/music/soundtracks`), `summary`, `years` (as in projects), optional `scoring` (what a piece is written for), `role` (what Nikola did), `image` (the card's square cover, a file name) and `links` (a list of `name` and an `https://` `url`, shown as buttons), then Markdown; images in `public/music/<slug>/`. Each tab lists the most recent first; `bands` and `soundtracks` can't be slugs. A missing or malformed field, or a missing image, fails the build.
- A player from Bandcamp, SoundCloud, Spotify or YouTube is written like an image on a line of its own, in any Markdown: `![Name](bandcamp:album/<id> "Caption")`, with `bandcamp:track/<id>`, `soundcloud:track/<id>`, `soundcloud:playlist/<id>` (the numbers in the services' embed codes), `spotify:album/<id>`, `spotify:track/<id>`, `spotify:playlist/<id>` (the id in the Spotify link) or `youtube:<video id>` (`youtube:<video id>?t=600` starts it at 10:00). It shows a button, and the service's own player loads only when it's pressed (`app/content/players.ts`, `Prose`), so nothing reaches the service before the reader asks. A malformed one, or one inside other text, fails the build.
- The About window's pages are `content/about/<page>.<lang>.md`, one file per language (`bio.en.md`, `bio.sr.md`, `bio.no.md`, `resume.en.md`); every page needs an English one. Front matter: `title`, `language` (its name in itself, as the switch shows it), `flag` (a country code with an SVG in `public/flags/`) and optional `pdf` (an `https://` link), then Markdown; images in `public/about/`. A page with more than one language gets the language switch. A new flag goes in `public/flags/` at 4:3, from flag-icons (MIT, notice in `public/flags/LICENSE.txt`) where possible. Any Markdown is rendered by `app/content/markdown.server.ts` and shown with the `Prose` component, so it reads and links like a post. A ` ```mermaid ` block becomes a diagram, drawn in the browser in the site's colours and drawn again when the theme or accent changes; Mermaid is fetched only on pages that have one, with the dagre layout (ELK is over a megabyte). A ` ```lyrics <song title> ` block is a song's words, folded under its title: stanzas split by empty lines, a line in brackets (`[CHORUS]`) at a stanza's start naming the part.
- The posts from the old WordPress site, and the pages listed in its `PAGES` (so far the About pages), were imported by `npm run import:wordpress` (`scripts/import-wordpress.ts`). Running it again overwrites them, so edits to an imported post or page are lost until the old site is gone and the script retired.
- Links to the old site (`/?p=<id>`, `/?page_id=<id>`, archives, feeds) are redirected to their new pages, from the table in `app/wordpress-redirects.ts` by `entry.client.tsx` and with the same rules in `public/.htaccess`. Change the two together; a test fails when they disagree. A page imported later can get its own path in both.
- Keep at least one post: with none, `blog/:slug` has a loader but nothing to pre-render, which React Router refuses with `ssr: false`.

## Git and pull requests

- `main` is the trunk. Branch from it as `feature/<issue>-<slug>`, `fix/<issue>-<slug>`, `chore/<issue>-<slug>` or `ci/<issue>-<slug>`.
- One logical change per commit. Short imperative titles; the body explains why, one line per paragraph, ending with `Refs #N`.
- PR descriptions list the commits and say "Closes #N". The owner reviews and merges every PR.
- No AI attribution lines in commits or PR descriptions.
- CI (format check, lint, typecheck, build) must pass before merging.
